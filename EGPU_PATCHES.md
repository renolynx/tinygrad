## Patch 25 (2026-09-02 evening, IN TEST): `schedule/memory.py::memory_plan_rewrite` holds buffers that are read before written

Under patch #7's "hold only tensor-reachable buffers" rule, a buffer whose data comes from outside the captured linear (the NPY source of a CPU->device copy of a conditioning tensor that the wrapper baked as a const, when that copy is too big for the prune to hoist) was planned into the arena and the replay read an unwritten slot. Symptom: Klein under the production `apply` capture = noise while the module capture was exact; Krea 2's conds are small enough to be hoisted, so it never hit this. ## Patch 24 (2026-09-02 evening, VERIFIED): `schedule/memory.py::_collect_bufs` follows view kernel args to the base BUFFER

## Patch 22 (2026-09-02 ~15:05, IN TEST): IQ3_S q8 decode kernel for NV (`_iq3s_decode_kernel` in amd.py, `iq3s_grid` uint32 table as a kernel input). IQ3_S = 27% of the Q3_K_XL bytes. 110-byte blocks are only 2-byte aligned and 3.3 GB of them cannot be repacked (no VRAM), so the packed view is **uint16** (`IQ3_HALFWORDS=55`) and words are assembled from halfwords. Detection: same 110-byte rate as Q3_K -> IQ3_S is recognised only when the dequant graph carries the 512x4 float grid BUFFER (`u.size == 2048`), and only with `_TARGET == "NV"` (AMD behaviour untouched). Signs: 1 bit per weight (set = negative) applied with a SWAR negate `(mag ^ m) + (m & 0x01010101)`, m = `((s4 * 0x204081) & 0x01010101) * 0xFF`. Gated by `LLM_NV_IQ3S=1` (default 0) after the first model run produced garbage ("用户teras不分teras…") although the unit test passed: `nv_tc/nv_iq3s_real_test.py` (real 27B tensors) showed eager PASS but **TinyJit replay garbage**, `nv_iq3s_jit_probe.py` (synthetic, seconds) bisected it to the kernel's UNUSED `xs` parameter: **a custom-kernel input that the kernel never reads breaks the JIT replay's argument mapping** (eager is fine; the earlier NOA ablation's "Device fault" was the same thing). Fix: the IQ3_S kernel takes only (out, raw16, xq, xd, grid). Rule for every future custom kernel: every placeholder must be read. The grid table is held on the layer (`self.iq3s_grid`, realized under ALLOW_DEVICE_USAGE=1).

**Chunk-64 finding (14:38, after fixing the #17 cap):** 27B at 8K context peaks at **15.72 GB** (+2.57 over the loaded model; chunk 32: 15.06) - 30 MB below the card's usable ~15.75 GB, so not adopted; 9B tokens 24/24 identical at chunk 64; the M=64 GEMM costs 1.45x M=32 per launch (32-row blocks on blockIdx.x, L2 sharing only partial). ## Patch 18 (2026-09-02): `LLM_DEQUANT_ONCE=1` - dequantize once per prefill chunk (`tinygrad/llm/kernels/amd.py` `Linear.__call__`, generic path)

On NV the generic Linear fuses the GGUF dequant into the matmul. ## Patch 17 (2026-09-02): env-gated chunked prefill for recurrent models on NV (`tinygrad/llm/model.py` `Transformer.generate`)

Upstream forces `chunk_size = 1` for Gated-DeltaNet models on any non-RDNA3 device (so on the 4080 a prompt is prefilled one token per forward through the decode graph = decode speed). `LLM_CHUNK=<n>` (default 1 = upstream) lets the prompt go through the symbolic prefill JIT in chunks of n using the unrolled Python scan (`for t in range(T_pad)`); upstream's own commit #17512 says that scan "is also faster chunked than token-by-token" and only gated it for CI time. Decode is unaffected (sampled tokens re-enter `generate` with a static (1,1) shape -> `rollout_jit`). Untested on the GPU as of the edit; the prefill graph's kernels need their own JITBEAM pass (matmuls with T=32, tensor cores applicable -> BEAM_VERIFY essential). **Fixed 2026-09-02 14:35:** the first form was `min(chunk_size, getenv("LLM_CHUNK"))` with generate()'s default `chunk_size=32`, so `LLM_CHUNK=64` silently ran as 32 — the first chunk-64 "checks" (identical VRAM peak, 24/24 identical tokens, a 4-minute campaign with 0 searches) were same-vs-same. Now `chunk_size = max(1, getenv("LLM_CHUNK", 1))`. Any future chunk change: confirm the kernel names carry the new T (e.g. `nv_f16_gemm_m64_...` under DEBUG=2) before trusting a comparison.

**Also on 2026-09-02, patch #9's `_fill_bufs_deterministic` was rewritten** to tile a 64-byte period (`bytes` multiplication) instead of `np.arange(n, uint32)`: the LLM decode kernels take views of the GGUF up to ~0.5 GB (LM head), and the numpy version spiked host RAM by ~2 GB per fill on a 16 GB machine. Pattern proven byte-identical. Its `BEAM_SEARCH: final tm=` audit line (BEAM_DEBUG=1) is now also printed in the verify branch, which used to return before reaching it.

## Patches 11-16 (2026-09-01/02): the beam worker pool actually works now

These five are what make `PARALLEL=8` beam/compile pools usable on this rig. The 2026-09-01 morning campaign ("campaign3") had been blamed on "worker recycling orphaning containers"; the logs say otherwise, and each real cause got its own fix:

- **#11 lazy docker compile container + respawn-once** (`device.py` `Compiler.compiler_process` property / `compile_via_server`; `compiler_cuda.py` stores `_server_args` instead of spawning in `__init__`). `Renderer.__reduce__` rebuilds a fresh renderer, hence a fresh `NVRTCCompiler`, on **every unpickle**, and the pool unpickles one per task, so every beam candidate spawned a `docker run` — measured 60 orphaned `Created` containers, a VM global OOM (5 compile servers killed), and the colima socket forwarder dying mid-search (`Cannot connect to the Docker daemon` ×20 in ts_tc512ta.log → `Broken pipe`). Now a container starts only on the first real compile, and a dead one is respawned once.
- **#12 workers never compile** (`codegen/__init__.py` `in_worker_process()` → `do_compile` leaves `BINARY(None)`; `finalize_program()` compiles in the parent; called in `search.py`'s beam loop (which also dedupes candidates by source text before compiling) and in `realize.py`'s `lower_and_compile`). Net effect: 8 workers do pure-Python lowering, the parent compiles serially through its single container (measured docker compile: p50 19 ms, p90 135 ms, p99 1.3 s, worst 35 s for a 566 KB source). `WORKER_COMPILE=1` restores upstream behaviour.
- **#13 flat UOp transport** (`engine/worker.py` registers `ForkingPickler.register(UOp, _reduce_uop)`): UOp graphs pickle recursively and the C pickler's recursion budget on python 3.12 is ~5000 frames **regardless of `sys.setrecursionlimit`** (measured: depth 3000 ok, 6000 fails). Every 1024px round of campaign3 died in 72-338 s with `RecursionError` in the pool's task feeder — NOT on docker. Graphs now cross the process boundary as a toposorted table; identity is preserved through UOp hash-consing (depth 30000 round-trips in 130 ms, `rebuilt is original`).

- **#14 parent/pool partition for lowering** (`realize.py` `needs_parent_lowering` predicate + partition in `lower_and_compile`; `tiny_ops_shim._install_selective_beam` sets the predicate to its loop-volume rule). Found by campaign attempt 1: with `PARALLEL=8` whole batches went to the pool, spawn workers have no shim monkeypatch, so big kernels silently skipped their beam search — 2 of ~23 rows banked, warm 512 = 612 s. Probe test [4]: 0 beamed without, 1 beamed with, on a mixed batch.

- **#15 bounded pool waits + parent fallback** (`worker.py` `pool_imap_bounded`, `POOL_TASK_TIMEOUT` default 1200 s; used by `realize.lower_and_compile` and `search.beam_search`). A worker that dies mid-task never delivers and `imap_unordered` hangs forever — measured 2026-09-01 18:34: one worker got `BrokenPipeError` on the pool's result queue during a 1024 compile batch (root cause of the EPIPE unexplained; the parent was alive) and the ComfyUI prompt hung for its full 3600 s budget. Now a result timeout tears the pool down, the parent lowers the missing kernels itself, and the next caller gets a fresh pool. Timeout path unit-tested (2 s timeout vs 6 s tasks → fallback + fresh pool).

- **#16 stub `__main__.__file__` during spawns** (`worker.py` `_stub_main_file`): upstream's `_without_main` sets `__main__.__file__ = None` while spawning a worker; any concurrent `inspect.getmodule()` in the parent then raises `TypeError: <module '__main__' from None> is a built-in module` — tinygrad's own scheduler does that under `DEBUG>=1` (caller file:line in the "scheduled N kernels" line), and a `maxtasksperchild` respawn from the pool's maintenance thread races it (killed a 512 campaign round 2026-09-02 05:57). Now `__file__` points at an empty stub the child imports as `__mp_main__`. Also set `BEAM_MAX_TASKS_PER_CHILD=1000000` (launcher, campaign) — recycling buys nothing once workers never compile.

**Proof:** `/Users/macmini/egpu/diagnostics/probe_pool_compile.py` — BEAM=2+BEAM_VERIFY on a half matmul with PARALLEL=4 (result correct, verify PASS logged), the parallel-lowering path (5 kernels correct), and the docker container count sampled throughout = **1**. Uses a throwaway `CACHEDB`.

**How to apply:** `PARALLEL=8 BEAM_MAX_TASKS_PER_CHILD=256` is now the right setting for any beam campaign and for the launcher. If a campaign ever shows `Broken pipe`/`RecursionError`/dozens of containers again, check these three greps first. `CACHEDB=<file>` points tinygrad at a different sqlite cache — campaigns run on a clone (`cache_tc.db`) so production `cache.db` is never at risk.

## Patch 7: TinyJit held_bufs disables the memory planner under eager capture (`tinygrad/engine/jit.py`, added 2026-08-31)

Upstream computes `held_bufs = set(buffers) | {tensor-reachable}` before planning. ## Patch 5: sysmem slab pool for the TinyGPU mapping quota (`runtime/support/system.py`, added 2026-08-31)

`APLRemotePCIDevice.alloc_sysmem` bump-allocates small requests out of 32 MB slab mappings (`SLAB_CHUNK`); only `contiguous` or >8 MB requests go straight to the helper (`_alloc_sysmem_direct` keeps the original body).

**Why:** the TinyGPU.app helper has a small fixed table of sysmem mappings — measured: a fresh process gets **~85** MAP_SYSMEM_FD calls before every further one fails — and the protocol has **no unmap command at all** (`PCIIfaceBase.free` is a no-op for remote sysmem), so mappings are process-lifetime. ## Patch 4: RPC reads the fd before checking the status (`runtime/support/system.py`, added 2026-08-31)

## Patch 3: no cyclic GC before giving up on an allocation (`tinygrad/device.py`, added 2026-08-31)

`LRUAllocator.alloc`'s recovery path was `except (RuntimeError, MemoryError): self.free_cache(); return super().alloc(...)`. A `gc.collect()` was added **before** `free_cache()`.

**Why:** CPython's cyclic collector is driven by object *counts*, not by bytes. A torch tensor on the tiny backend is a handful of small python objects in a reference cycle pinning a multi-MB device buffer, so the collector has no idea the card is full and the generational thresholds are never tripped by GPU pressure. Measured under ComfyUI on the 16 GB card at the moment of failure: `GlobalCounters.mem_used_per_device["NV"]` read **9519 MB**, and one `gc.collect()` took it to **2733 MB** — 6.8 GB was unreachable garbage. `free_cache()` alone could not recover it because those buffers had never been freed in the first place.

**Symptom without it:** the second image in a process dies with `MemoryError: Allocation of 432.00 MB failed on NV. Used: 15.02 GB` (inner cause `Failed to allocate memory (OOM). Request size=0x1b000000 ((4096, 4096))` from `support/memory.py`). This is a *different* failure from Patch 2's `Device fault detected` and only became visible once Patch 2 removed the MMU fault that was killing prompt 2 earlier.

**How to verify it is still applied:** `grep -n "gc.collect()" tinygrad/device.py` — expect a hit inside `LRUAllocator.alloc`. Also `grep -n "^import.*struct, gc" tinygrad/device.py` for the import.

## Patch 2: GSP-owned vram handed out as tensor storage (`runtime/support/nv/nvdev.py`, added 2026-08-31)

`_early_mmu_init` used to build the memory manager with `self.vram_size - (64 << 20)` under the comment "tail vram reserved for falcon structs". Changed to `(256 << 20)`.

**Why:** `NV_GSP.init_wpr_meta` (`support/nv/ip.py`) carves the top of vram for the GSP firmware — VGA workspace, FRTS, bootloader, the radix3 ELF, and `gspFwHeapSize = 0x8100000` (129 MB). A shader writing there raises MMU `NV_PFAULT_FAULT_TYPE_REGION_VIOLATION`, which surfaces as the bare `RuntimeError: Device fault detected`. This is what limited ComfyUI to one image per process for weeks.

**How to verify it is still applied:** `grep -n "256 << 20" tinygrad/runtime/support/nv/nvdev.py`. If the eGPU starts raising "Device fault detected" again after a pull, this is the first thing to check. Costs 192 MB of a 16 GB card.

**Patch #30 (2026-09-04) — host-side shadow of the GPU page tables (`runtime/support/nv/nvdev.py` + `runtime/support/memory.py`). **Patch #31 (2026-09-04) — freeing a base buffer must invalidate its views (`tinygrad/device.py`). This is a real tinygrad correctness bug, not an eGPU quirk.** `Buffer.allocate()`'s view branch caches the view's pointer as `allocator._offset(base._buf, nbytes, offset)` in the VIEW's own `_bufs`, and `Buffer.deallocate()` on a base never clears it — it only decrements a count. Since `is_allocated()` on a view delegates to the base, once the base is re-allocated ELSEWHERE every view still reports itself initialized and hands kernels a pointer into the old allocation. `get_buf()` returns the cached `_bufs` entry directly, so `ensure_allocated()` is not even consulted. It is invisible while the freed block comes straight back out of the LRU cache at the same address, which is why it hid for weeks. Fix: views register themselves on their base (`base._views`, a WeakSet created lazily) and a base's `deallocate()` clears each view's `_bufs` and resets `allocated_views`.

**How it surfaced:** ComfyUI's memory reclaim calls `CapturedJit.free_intermediates()` (buffers go to the LRU cache, still mapped) and then `allocator.free_cache()` (really unmapped), and the next TinyJit replay wrote into the unmapped memory-planner arena — `NV_PFAULT_FAULT_TYPE_PDE`, WRITE, at an address the map log showed unmapped. Klein 9B faulted on every second prompt.

**Repro:** `diagnostics/jit_free_replay_repro.py`, ~15 s. Needs all three of `FREE_INTER=1`, `FREE_CACHE=1` and the memory planner; `NO_MEMORY_PLANNER=1` or dropping either call makes it pass. After the patch all variants pass, and Klein runs its second prompt with the capture kept (`TINY_JIT_RECLAIM_KEEPS_CAPTURE=1`) with **0 faults** and both MPS quality gates passing.

**Verify:** `grep -c "_views" tinygrad/device.py` -> >=3. Symptom if lost: `RuntimeError: Device fault detected` on the second prompt of any ComfyUI session where a reclaim fires, and `diagnostics/jit_free_replay_repro.py` returning RESULT FAULT.

**Note:** the ComfyUI-side workaround (the reclaim dropping a capture that actually freed memory) is now **off by default** - #31 fixes the root cause, and dropping the capture would needlessly send the next prompt back to eager submission. `TINY_JIT_RECLAIM_KEEPS_CAPTURE=0` turns the drop back on as the belt-and-braces path if #31 is ever lost. LLM prefill chunk (M<=64, the weight is read exactly once, bandwidth-bound), useless for a DiT step where M is the
whole packed sequence (8640 rows at 640x352) and the four Q3_K linears per block are the entire compute budget.

Design: a block owns a BM x BN output tile with (BM/WM)*(BN/WN) warps of WM x WN each = (WM/16)*(WN/8) mma
accumulators in registers (32 at the default 128x128 block, 32x64 warp). **No shared memory** - inside a block the
warps sharing a column strip issue identical weight loads and those sharing a row strip identical activation loads,
and L1 dedupes them (a 32-wide k slice of the tile is 16 KB against a 128 KB L1); staging through shared memory is
the obvious v2 and was not needed. Same 32-wide k permutation as #19/#23 (lane t owns k = 8t..8t+7, one uint4 per
row) applied identically to A and B, so the fragment layout costs no shuffles. Ragged M: loads clamped to M-1,
stores predicated. **Block swizzle** (G consecutive n-blocks x every m-block per group) is worth 40%: at the qkv
shape G=1 gives 75 TFLOPS, G=4 98, G=12 103; `nv_tc_gemm_config` picks the divisor of N/BN nearest 12.

Measured on the 4080 at the H3 640x352 shapes (M=8640, bf16 in and out, `diagnostics/nv_gemm/bench.py`):
qkv 21504x5376 19.3 ms, out_proj 5376x7168 6.5, fc1 28672x5376 26.5, fc2 5376x14336 13.0 = **65.3 ms per block,
102 TFLOPS**, against 176.6 ms (37.7 TFLOPS) for the beam-tuned generic kernels = **8.83 -> 3.26 s per 50-block
step**. 102 TFLOPS is ~97% of the card's 104 TFLOPS fp16-with-fp32-accumulate peak (consumer Ada does NOT halve
the fp32-accumulate rate; the flash kernel's 73 TFLOPS had already ruled that out).

Tile sweep at those shapes (total TFLOPS): 128x128 warp 32x64 U1 = **102.9**, warp 16x128 101.3, 128x256 warp
32x128 98.9, 256x128 warp 32x64 98.7, 64x128 warp 32x64 96.9, warp 32x32 94.7, warp 64x32 U2 91.9, warp 32x64 U2
91.6, warp 64x32 U1 82.5. Env overrides `NV_GEMM_BM/BN/WM/WN/U/G` for re-tuning.

**Model result (640x352, 8640 packed rows):** a sampling step 12 -> 7 s under the production JIT replay
(`dit_test.py`, 4 steps: eager 216 -> 205 s, capture 55 -> 48, replay 12/12 -> 7/7); a full 8-step fox clip in the
server 435 -> 375 s. Pixel gate against the same prompt/seed with the flag off: overall mean abs 19.38/255

## Patch 43 (2026-09-06): flash kernel tile shape 8 waves x 80 keys (`NV_FLASH_WAVES`, `NV_FLASH_BN`)

## Patch 45 (2026-09-08): `TINY_ALLOC_LOG=1` - log the LRUAllocator's allocation-recovery path (`tinygrad/device.py`)

The recovery path (free_cache -> gc.collect -> retry) is silent, so a phase that is slow because every allocation fails and
collects the whole heap looks identical to one that is slow for any other reason. With the flag each failure prints the
size and the used total, and each gc.collect its duration, to stderr. Written while chasing a 92 s Flux2 VAE decode at
1024 px; the answer there was NOT this path (0 recoveries) but a BEAM winner with zero opts (fixed in ComfyUI's
`tiny_ops_shim._selective_apply_opts`, 2026-09-08). Verify: `grep -c "alloc recovery" tinygrad/device.py` -> 2.
